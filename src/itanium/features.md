## Grammar ##
The grammar deviates in several places from the one published on [itanium-cxx-abi.github.io](https://itanium-cxx-abi.github.io/cxx-abi/abi.html#mangle.type)

* we dropped support for anything that cannot be generated by either GCC or clang, mostly C types not accepted in C++ mode like imaginary types or saturated integers
* all non-terminal names are valid C++ identifiers (hyphens have been replaced with underscores)
* The published grammar is plain wrong when it comes to where abi-tags are allowed (it makes no sense to only allow them on operator names)
* We use an incompatible definition for closure-prefix. All demanglers have to deal with the problem that the grammar as written will lead into infinite recursion when parsing prefixes
* We have introduced many additional non-terminals (e.g. `pointer_type` and `reference_type`) to capture more semantic information in the AST generated from demangling
* The published grammar is inconsistent in its style (sometimes a list of things as encoded with repetitions `x := <item>+`, sometimes as a recursive list `x := item [<x>]`)
* `special-name`s are not instances of `<name>` and have been renamed to `special_object`
* Very many things used by both clang and GCC or only one of them are not mentioned in published grammar but have been added to this demangler (e.g. C++20 concepts and requirements, C++23 deducing this)
* The grammar is considered unstable for now. The plan is to serialize the AST derived from the grammar to stable JSON format eventually.
* There will be more stylistic changes to the grammar in the future, e.g. we plan to replace
```
pack_indexing_type := "Dy" <type> <expression>
                   := "Dy" <template_arg_pack> <expression>
```
with
```
pack_indexing_type := "Dy" { <type> | <template_arg_pack> } <expression>
```
to have a more concise grammar

## Parsing ##
The parser has been written from scratch and is not based on either libiberty or the LLVM implementation. That includes their test suites.
Currently, the CI tests all C++ symbols found in the generated binary and compares demangling against llvm-cxxfilt. It is not possible to test automatically against c++filt because it has been severely neglected and cannot demangle any of the C++20 or later features used by GCC when mangling.
The goal for happy-path testing is to collect all mangling tests from GCC and clang releases and make sure those are handled successfully.
The repo includes code for building the demangler with the AFL+ fuzzer. Running the fuzzer is not part of the CI.
The goal for the parser is to successfully parse all mangled names generated from recent released versions of GCC and clang.


## Mangling ##
The parser converts mangled names to an AST. It is possible to do a lossless roundtrip from mangled name to AST back to mangled name or from AST to mangled name back to AST when starting with a mangled name or AST coming from valid C++. The grammar is ambiguous without that restriction: `_Z1fcm` can be parsed as `f(char, unsigned long)` or as `f(operator,)` where `operator,` is parsed as `<type> -> <class-enum-type> -> <name> -> <operator-name>`.
One of the goals is the ability to compute the mangled names of the types of function parameters, e.g. to derive `N3foo6VectorIiEE` from `_ZN3foo1fIiEEvNS_6VectorIT_EE`. That requires the ability to apply substitution compression in the compression direction as well as the decompression direction.


## Performance ##
This demangler is quite slower than other implementations. The assumption is that the demangler only needs to be as fast as a human can read.
On the other hand, the parser and mangler are expected to be used in an automated fashion when checking for ODR violations on large codebases.
The implementations will be profiled and optimized as necessary.


## Relative Names ##

Assume the following function
```
namespace foo {
    struct bar {};
    struct baz {};
    template<typename T>
    void qux(bar);

    template<>
    void qux<baz>(bar){}
}
```

This will be mangled as `_ZN3foo3quzINS_3bazEEEvNS_3barE` and usually demangled as `void foo::qux<foo::baz>(foo::bar)`. The demangler is for use in a source-level debugger, we want demangled output to match the source code that generated it.
When the "Relative Names" feature is active, this will be demangled as `void foo::qux<baz>(bar)`, namespaces that are part of the function name will not be repeated in template arguments or function arguments. This feature does not rely on external configuration data.

## Inline Namespaces ##

When demangling `_Z1fNSt3__16vectorIiNS_9allocatorIiEEEE`, the output is `f(std::__1::vector<int, std::__1::allocator<int>>)`. The demangler is for use in a source-level debugger, we want demangled output to match the source code that generated it. Which means hiding inline namespaces. That would demangle the function as `f(std::vector<int, std::allocator<int>>)`.
It is not part of the mangling whether a namespace is an inline namespace, this information needs to come from configuration data (serializable as JSON), it will not be hard-coded.
This configuration data can be automatically generated from DWARF debug information, which can mark namespaces as inline.

## Default Template Arguments ##

When demangling `_Z1fNSt3__16vectorIiNS_9allocatorIiEEEE`, the output is `f(std::__1::vector<int, std::__1::allocator<int>>)`. The demangler is for use in a source-level debugger, we want demangled output to match the source code that generated it. Which means hiding default template arguments. That would demangle the function as `f(std::vector<int>)`.
It is not part of the mangling whether a template argument has been defaulted, this information needs to come from configuration data (serializable as JSON), it will not be hard-coded.
This configuration data can be automatically generated from DWARF debug information, which can mark template arguments as default (but compilers don't always do that).
Unlike inline namespaces, which can be just a list of strings, this will require describing patterns which are then matched against the intermediate AST obtained from parsing the demangled name.

## Typedefs (and other aliases)##

When demangling `_Z1fSt17basic_string_viewIcSt11char_traitsIcEE`, the output is `f(std::basic_string_view<char, std::char_traits<char> >)`. The demangler is for use in a source-level debugger, we want demangled output to match the source code that generated it. Which means using common typedefs for common types. That would demangle the function as `f(std::string_view)`.
Resolved typedefs are not part of the mangling, this information needs to come from configuration data (serializable as JSON), it will not be hard-coded.
This configuration data can technically be automatically generated from DWARF debug information, but we don't want to use every typedef, there needs to be some curation.
It might be reasonable to ship a default config for the two supported standard library implementations and allow users to provide their own lists.

## Argument Names ##

Function parameters and template parameters have names in the source code. When using the demangler to display names obtained from debug information, it should be able to be augmented with that information. Other information included in debug information are unmangled return types and the `[[noreturn]]` attribute. Most other attributes and all reflection annotations can only be extracted from parsing C++ source code.

## Linear Names ##

Because substitutions are used to compress mangled names, it is possible for the length of the demangled output to be exponential in the length of the mangled input.
Not resolving substitutions makes the output length linear in the input length. For an unambiguous output, we need to explain what each used substitution refers to.
If we restrict ourselves to one-line output, a possible output would be `longname::f(S::bar, S0&, S1) using S = longname, S0 = S::bar, S1 = S0&`.
For multiline output, the options are
```
longname::f(S::bar, S0&, S1)
using
  S = longname
  S0 = S::bar
  S1 = S0&
```
and
```
longname::f(S::bar, S0&, S1)
^^^^^^^^    ^^^^^^  ^^^     
   S          S0    S1
```
which becomes a bit more complicated with more nesting levels
```
long::name::f(S0::bar, S1&, S2)
^^^^  ^^^^    ^^^^^^^  ^^^     
 S     S0       S1     S2
```

## Integrations with other software ##

It is not recommended to use the software in this repo to build a shared library capable of replacing `__cxa_demangle` in other software via `LD_PRELOAD`.
You can use this project's binary as a filter on the output of command line tools like `nm` or `readelf`. TUI and GUI applications like `perf` and `kcachegrind` that would profit from an improved demangler need actual refactoring so they can provide the demangler with length information and demangling options.
An FFI API that would allow other software to use this demangler with user-controllable configuration options while maintaining low coupling has not been finalized.

Maybe 
```
extern "C" {
struct FfiDemangler;
int create_demangler_from_options_string(sizet_t nlen, const char*, FfiDemangler** output_ptr);
int create_demangler_from_json_options(size_t nlen, const char* , FfiDemangler** output_ptr);
void free_demangler(FfiDemangler*);
ssize_t demangle(FfiDemangler*, size_t mangled_len, const char* mangled, size_t buffer_len, char* buffer);
ssize_t demangle_best_effort_length(FfiDemangler*, size_t mangled_len, const char* mangled, size_t buffer_len, char* buffer, size_t best_effort_length);
}
```

for a plugin-style API with error codes for creation failures and demangling failures.

which would allow users to supply a demangler-specfic options string like "tdC" for _trailing return type, show details, integer literal suffix in CAPS_ instead of putting the same thing in a JSON config.
